# Offline wrap

How The Strip installs, and how it plays with the network cut. ROADMAP item 12.

The game needed almost nothing to become offline-capable: `src/` contains no
`fetch`, no `XMLHttpRequest` and no external URL, and the daily seed is computed
from the local date. Only the wrapper was missing. The service worker started as
a copy of `timeholder/sw.js`, which has been doing this job for a different app
of the owner's for a while; the differences below are the places where copying
it verbatim would have been wrong, and each cost something to find out.

## What ships

| File | Role |
|---|---|
| `public/manifest.webmanifest` | install metadata — static, one file for every deployment |
| `public/icon.svg`, `public/icons/*.png` | the icon set, generated by `scripts/icons.mjs` |
| `scripts/sw-template.js` | the service worker, **before** the build fills it in |
| `offlineWrap()` in `vite.config.ts` | emits `sw.js` into the build output |
| `launcher/serve.sh` | the macOS runtime-detection ladder — **sourced by both mac launchers**, one copy |
| `launcher/The Strip.command` | the loose-script launcher, for the mac zip |
| `launcher/app-main.sh` | the executable inside `The Strip.app` |
| `launcher/win/serve.ps1` | the Windows server — no ladder needed, PowerShell *is* the runtime |
| `launcher/win/the-strip.ico` | the shortcut's icon (deliberately **not** in `public/`) |
| `scripts/pack-offline.mjs` | builds `release/*.zip` for itch.io + macOS |
| `scripts/pack-app.mjs` | builds `The Strip.app` + `The-Strip.dmg` |
| `scripts/pack-win.mjs` | builds `release/the-strip-offline-windows.zip` |

Two ways to play offline, and they are genuinely different:

* **Installed PWA.** Open the game once online, let the browser install it
  (Chrome/Edge "Install", Safari "Add to Dock"), and from then on it launches
  from the Dock with no network. Needs that one online visit — a worker can only
  cache what it was allowed to fetch.
* **The downloadable package.** `release/the-strip-offline-macos.zip` (a folder
  with a `.command`) or `release/The-Strip.dmg` (drag the `.app` to
  Applications) never needs a network at all. Neither can be a plain
  double-click on `index.html`, because the bundle is an ES module and browsers
  refuse modules over `file://`; both start a local server on 127.0.0.1 instead,
  borrowing whatever runtime the Mac already has (python3 / php / node / ruby).

### The local server is a bootstrap, and the launchers now act like it

**Once the service worker is installed, the server can die and the game keeps
working.** Measured, not assumed — `npm run persist` kills the serving process,
closes the whole browser, reopens the same profile cold and plays a run:

```
seeded: true · serverDead: true · coldNavigationOk: true
bundleRan: true · playableFromColdStart: true · failedRequests: []
```

So the launchers **seed and quit**. They serve the folder, open the browser, wait
for the request stream to go quiet, then shut the server down and exit — around
8–13 s in practice. The first version instead blocked on a dialog whose only
button was Quit, which meant a modal on every launch and a server still listening
long after the player had closed the tab.

The waiting is quiescence-based, not a file count. `wait_until_served` in
`serve.sh` first compared what had been served against `find . -type f`, a number
it can never reach: the folder also holds the launcher, `serve.sh` and the READ
ME, and a browser never asks for those. It waits in two phases:

1. **until the browser connects at all** (cap 300 s) — a Mac that takes 40 s to
   launch a cold browser must not have its server killed before a byte moves;
2. **until three quiet seconds** (cap 25 s) once traffic has started.

The timeout is the contract; log parsing only finishes sooner. `php` and `ruby`
do not log in a readable shape, so with them it falls back to a flat wait rather
than pretending — 140 kB over loopback is never what takes the time.

The install hint is a **notification, shown once**, marked by
`~/Library/Application Support/The Strip/install-hint-shown`.

## The three decisions worth keeping

### 1. The precache list is generated, never written by hand

Timeholder's worker lists its files literally. That works there because its
filenames are stable. Vite hashes them (`assets/index-BPX8hsJF.js`), so a
hand-written list would name a bundle that no longer exists on the very next
build — and the failure is silent until someone goes offline.

`offlineWrap()` therefore reads the list back **off disk** in `closeBundle`,
after Vite has finished writing. Reading the bundle graph instead would miss
everything copied out of `public/` (manifest, icons). The cache name is a SHA-1
of every shipped byte, so an identical rebuild does not churn the player's
storage and a changed one always rolls over.

The plugin throws if any `__PLACEHOLDER__` survives substitution. That check
exists because the first version matched bare placeholder names and filled the
template's own header comment instead of the constant, shipping an `sw.js` whose
`PRECACHE` was the literal string `__PRECACHE__`.

### 2. `ignoreVary: true` on every cache read — not optional

This one is invisible until you cut the network, and then nothing works.

`cache.addAll()` fetches with mode `no-cors`, so the stored entries carry no
`Origin` header. The page then asks for its module with `crossorigin` (Vite
emits that attribute on the module script), which **does** send one. Any server
answering `Vary: Origin` — `vite preview` does, and CDNs commonly do — treats
those as two different requests. Every lookup misses, the game dies offline with
`ERR_FAILED` on its only script, and the cache sits there full the whole time.

Ignoring `Vary` is safe here because every cached URL is a static, same-origin
file whose bytes do not depend on any request header.

### 3. The dev guard lives at registration, not inside the worker

Timeholder's worker checks `location.hostname` and bypasses its cache on
`localhost`. Copying that would have made the offline wrap **untestable**:
`vite preview` serves the production build on localhost, which is exactly where
`scripts/offline.mjs` proves the game runs with the network cut. A hostname
guard would have turned that proof into a no-op that passes for the wrong
reason.

So the guard is `import.meta.env.PROD` at the registration site in `main.ts` —
`npm run dev` never registers a worker at all, which is the actual thing worth
preventing (a worker shadowing HMR and serving stale modules looks exactly like
your own bug). The worker itself has no environment checks.

## Caching strategy

| What | Strategy | Why |
|---|---|---|
| `assets/*` (hashed) | cache-first | a changed byte means a changed filename, so the cached copy can never be stale |
| `index.html` (navigations) | network-first, cache fallback | the one mutable name in the build: online players always land on the current version, offline players on the last one seen |
| everything else | cache-first | icons and the manifest, all content-stable |

`skipWaiting()` + `clients.claim()` are used deliberately. The game is a single
bundle with no dynamic imports, so there is no chunk a running page could ask
for and miss; without them a new build would sit idle until every tab was
closed. `activate` deletes only caches prefixed `the-strip-` — github.io is one
origin for the whole portfolio, and an unprefixed sweep would wipe the other
games' caches.

## One build, two bases

`vite.config.ts` keeps `base: '/minefield/'` for GitHub Pages. The offline and
itch.io packages are built with `--base=./` into `dist-offline/` — itch serves
HTML games from a path it chooses, so anything absolute 404s there.

`index.html` never hard-codes either: every `href` goes through Vite's
`%BASE_URL%` placeholder, and `manifest.webmanifest` keeps `start_url`, `scope`
and every icon `src` relative, so the same file is correct under both.
`test/pwa.test.ts` guards exactly this.

## Scores do not follow you between installs

`localStorage` is scoped to the **origin**, and the game's save keys
(`minefield` in `save.ts`, `minefield-hiscore` in `highscore.ts`) live there. So
every way of reaching the game has its own separate table:

| Where you play | Origin | Its own save + high scores |
|---|---|---|
| GitHub Pages / the installed PWA | `https://zrebec.github.io` | yes |
| the macOS offline package (`.command` or `.app`) | `http://127.0.0.1:8137` | yes, separate |
| the Windows offline package | `http://localhost:8137` | yes, separate again |
| `npm run preview` | `http://localhost:4173` | yes, separate |
| itch.io | `https://html-classic.itch.zone` | yes, separate |

Browsers do not share with each other either, so Firefox and Safari on the same
address are two more tables.

Verified, not assumed: a key written on `localhost:4173` is invisible from
`127.0.0.1:8137` and still there on returning to `4173`. This is the web's
security model, not a bug we introduced, and **no amount of launcher work can
change it** — only moving the data can.

The one thing we do control is the port, and it is why `8137` is hard-coded in
`serve.sh`: a launcher picking a free port at random would hand the player a new
origin — and a blank score table — on every single launch.

Carrying scores across would mean exporting the save. The envelope is already
versioned and signed (zx-kit `save`, v6, FNV-1a), so a copy-paste code is
plausible — but that is a **new feature and v1.0 is frozen**, and it is the same
machinery as the replay-code idea, so building it twice would be a waste. Treat
each install as its own console until then, and say so on the itch.io page.

**What we do instead of staying silent:** the title screen prints the host above
the high-score table (`scoreProfile()` in `highscore.ts`, drawn on row 12 in
`renderIntro`), and the screen-reader menu mirror says it in words
(`STR_A11Y_MENU_PROFILE`). Both are built locally from `location.host` rather
than the `L.STR_*` pack for the visual one — a host is a value, not prose, the
same reasoning as the `L: EN` language indicator two rows below it. A player who
sees their scores "vanish" now has something on screen that explains it.

## Windows

`npm run pack:win` → `release/the-strip-offline-windows.zip`. Unzip, double-click
**The Strip.cmd**; run **Create desktop shortcut.cmd** once for an icon.

There is **no runtime ladder** here and that is the interesting part. macOS may
or may not have python3/php/node/ruby, so `serve.sh` has to hunt. Every Windows
10+ install ships PowerShell, and PowerShell has `System.Net.HttpListener` — so
the server *is* `serve.ps1`. Nothing to detect, nothing to install, and the "your
machine has no runtime" failure mode simply does not exist.

Three details that are load-bearing:

* **The prefix is `http://localhost:8137/`, not `127.0.0.1`.** Windows lets a
  normal user reserve the loopback *name* without an admin URL ACL; the numeric
  form would demand one. Consequence: the Windows origin is `localhost:8137`
  while macOS is `127.0.0.1:8137`, so the two keep separate score tables.
* **One pending `GetContextAsync()`, carried across loop iterations.** Calling it
  inside the poll loop queues a fresh accept every 500 ms and abandons the last
  one; when a request finally arrives, any of those hundreds of pending tasks may
  be the one to receive it while the variable being waited on never completes —
  server idling, browser hanging on a request it had already accepted.
* **The game lives in `game/`,** not beside the scripts, so the server cannot
  serve its own source. (The macOS zip is flat instead, because there the
  `.command` has to sit next to `index.html` for a double-click to make sense.)

The `.ico` is written to `launcher/win/`, **not** `public/`: anything in `public/`
is copied into every build and then precached, so a Windows-only icon would ship
to every web player and sit in their cache for nothing. It is packed by hand in
`scripts/icons.mjs` (`toIco`) — header, directory, PNG payloads, which the format
has allowed since Vista. That is ~30 lines against a dependency, and the output
is verified with `file(1)` and ImageMagick rather than trusted.

**None of the Windows path has been executed.** There is no Windows machine and
no `pwsh` here, so it has been reasoned and read, not run. Expect one round of
fixes on first contact.

## The .app bundle

`npm run pack:app` builds `release/The Strip.app` and a drag-to-Applications
`The-Strip.dmg`. No packaging tool is involved: a `.app` is a directory with an
agreed shape, and `sips` + `iconutil` (both stock macOS) turn `icon-1024.png`
into the `.icns` Finder wants. Every size is downscaled from the same 1024
master, so nothing is ever upscaled.

Two things it buys over the `.command`: the real icon in Finder and the Dock,
and no Terminal window — a bundle's executable runs headless.

That second one creates the problem the dialog solves. A shell script has no
`NSApplication`, so nothing answers Cmd+Q; without a blocking prompt the only
way to stop the server would be Force Quit. So `app-main.sh` ends on an
`osascript` dialog whose single button is Quit, and the `trap` takes the server
down with it. It doubles as the one screen a player will read, which is where
the "install it from your browser" hint goes.

`serve.sh` is shared between the two launchers rather than copied. It is the
only fiddly part of either (the python3 → php → node → ruby ladder, and the
explicit MIME map in the node fallback — a `.js` served as anything but
`text/javascript` is a black screen), so two copies would drift the first time
one got fixed. `pack-offline.mjs` therefore ships `serve.sh` beside the
`.command` in the zip, non-executable on purpose so it does not look like a
second way to start the game.

## Icons

`scripts/icons.mjs` is the source of truth: an SVG motif, rasterised to PNG in
headless Chromium (Node has no SVG renderer; same devDependency as
`capture.mjs`). Regenerate with `npm run icons mine`; `npm run icons --
--candidates` renders the alternatives that were considered.

The 8×8 sprite rule from `AGENTS.md` governs the 256×192 playfield, not a
1024 px icon in the Dock — but the palette does carry over: every colour comes
from `zx-kit`'s `C`, and there are no gradients, because a Spectrum cannot make
one. Shading is the machine's own normal/bright pair (`C.RED` → `C.B_RED`).

There is no separate maskable *artwork*. The motif's widest point is a horn tip
at radius 173 of the 256 half-viewBox — 68 % diameter, comfortably inside the
80 % circle Android crops to — so the same files serve both purposes. **If the
artwork ever grows past that, withdraw the claim rather than keep it.**

But they are listed as **separate manifest entries**, `purpose: "any"` and
`purpose: "maskable"`, and that is not tidiness — it is a bug fix.

The first version declared every icon `"any maskable"`, which reads as the
honest description of a full-bleed icon that survives cropping. **WebKit skips
it.** Safari parses `purpose` and uses only icons whose value is `any` (or that
have no purpose at all); anything containing `maskable` is passed over. With all
four icons marked `"any maskable"`, Safari's *Add to Dock* found nothing it would
use and fell back to drawing the first letter of the name. The evidence is in the
web app Safari generates:

```
$ plutil -p ~/Applications/The\ Strip.app/Contents/Info.plist | grep IconKind
  "WKManifestIconKind" => "Monogram"
```

Everything else in that file — name, colours, category, scope — came through
correctly, so the manifest was being read and understood. Only the icons were
rejected, and silently.

Two consequences worth keeping:

* **A raster `any` icon must always be in the list.** The SVG is listed last
  among the `any` entries on purpose; Safari's SVG support here is not something
  to bet the icon on.
* `test/pwa.test.ts` fails if `"any maskable"` ever comes back. The acceptance
  test for a change to this list is the `plutil` line above reporting anything
  other than `Monogram`.

## Verifying

```bash
npm test              # test/pwa.test.ts — manifest/index/template contract, no browser
npm run build
npm run smoke         # gameplay over the production build (unchanged by the wrap)
npm run offline       # THE one that matters: install the worker, cut the network,
                      # reload, and play a run with it still cut
npm run persist       # survives the launcher quitting: kill the server, close the
                      # browser, reopen the same profile cold, play a run
npm run pack:offline  # release/the-strip-web.zip + release/the-strip-offline-macos.zip
npm run pack:app      # release/The Strip.app + release/The-Strip.dmg
npm run pack:win      # release/the-strip-offline-windows.zip  (UNTESTED — no Windows here)
```

`npm run offline` asserts `allFromServiceWorker` — Chromium's own answer to "did
this response come out of the cache we built" — and `playableOffline`, which
starts a real run after the network is gone. A registered worker, a populated
cache and a green Lighthouse score are all circumstantial next to that.

## Known limits

* **Do not install from the launcher's URL — and it is worse than it sounds.**
  The obvious version of this warning is "a Dock icon pinned to
  `http://127.0.0.1:8137/` is dead whenever the launcher is not running". True,
  but it misses the real trap, which we walked into: **a Safari web app does not
  inherit anything from Safari.** It gets its own sandboxed container —

  ```
  ~/Library/Containers/com.apple.Safari.WebApp/     # exists, and is EMPTY
  ```

  — with no service worker and no cache of its own. So *Add to Dock* from the
  local address produces an icon that looks perfect (right name, right mine
  icon) and fails on first launch: empty profile → straight to the network →
  the launcher shut down minutes ago → "cannot connect". The player has no way
  to guess why.

  For the local package, **`The Strip.app` is the Dock icon.** Drag it over from
  the disk image. Safari's *Add to Dock* belongs to the hosted build, where the
  server is the internet.

  This is also the limit of what `scripts/persist.mjs` proves: it reuses one
  persistent Chromium profile, so it shows the game survives a dead server and a
  browser restart — it does **not** model a fresh storage partition, which is
  exactly what a Safari web app is. Do not read it as covering that case.
* **Safari has no install prompt.** Chrome and Edge offer *Install*; Safari (17+,
  and still so in 26) hides the same thing under **File → Add to Dock…** or the
  Share menu. Nothing is missing — it is just never advertised, so players will
  not find it on their own. Say it explicitly on the itch.io page.
* **Scores are per-origin** — see the table above. Each install is its own
  console.
* **The macOS launcher needs a runtime the Mac already has.** python3, php, node
  or ruby, in that order. If none is present it says so and points at the web
  version. Shipping a binary to close that gap is a different project. Windows
  has no such gap (PowerShell is always there).
* **The whole Windows path is unrun.** Written and reasoned, never executed —
  there is no Windows machine and no `pwsh` here.
* **Nothing is code-signed anywhere.** On Windows that surfaces as SmartScreen
  ("Windows protected your PC" → More info → Run anyway) on a downloaded `.cmd`.
  On macOS it is Gatekeeper, and it hits the `.app` harder than the
  `.command`: quarantine applies to anything downloaded from the internet. For
  a loose script the prompt is a nuisance; for an unsigned `.app` on macOS 15+
  the right-click → Open bypass is gone and the player has to go to **System
  Settings → Privacy & Security → Open Anyway**. That is why the `.zip` stays
  the itch.io download and the `.dmg` is for handing over directly or for your
  own Dock. Locally built copies are never quarantined, so on this machine none
  of it applies. Fixing it properly needs a paid Apple Developer ID; a stopgap
  for a specific recipient is `xattr -d com.apple.quarantine "The Strip.app"`.
* **itch.io serves HTML games in a sandboxed iframe,** where service worker
  registration can be refused. The registration is in a `try`/`catch` and the
  game runs fine without it — it only loses the ability to start a second time
  with no server.

## What is generic, and where the seams are

ChaosBunny and IceHaul will want this too, so this section records what would
move into a shared tool and what would not. **It is a map, not a plan.**
`retro/docs/sk/pwa-distribucia.md` §7 already sequences the work — Minefield is
the pilot, extraction happens when the recipe has settled and a second game
actually asks — and `ROADMAP.md` carries the same rule for zx-kit itself:
*extraction deferred until a 2nd real consumer.* Nothing here should be built
before then. Written down now only because the reasoning is cheap today and
expensive to reconstruct in December.

Note that Minefield is the **awkward** consumer, not the representative one:
ChaosBunny and IceHaul already build with `base: './'`, so the two-build dance
in *One build, two bases* above is a GitHub-Pages problem that only this game
has.

### Measured split

| | lines | notes |
|---|---:|---|
| `launcher/serve.sh` | 127 | **zero game knowledge** — takes `$PORT` and a cwd |
| `launcher/win/serve.ps1` | 138 | port + one URL in an error message |
| `scripts/sw-template.js` | 82 | one cache prefix, already a build-time placeholder |
| `offlineWrap()` in `vite.config.ts` | 48 | reads `outDir`/`base`/version — nothing else |
| `scripts/pack-{offline,app,win}.mjs` | 247 | name, bundle id, icon paths |
| `launcher/win/*.cmd`, `shortcut.ps1` | 52 | name only |
| **near-generic subtotal** | **~695** | |
| `scripts/icons.mjs` | 237 | machinery generic; the three motifs (~60) are Minefield's |
| `launcher/*.command`, `app-main.sh` | 135 | structure generic, wording is this game's voice |
| `test/pwa.test.ts` | 156 | the PWA contract is generic; expected values are not |
| `scripts/{offline,persist}.mjs` | 185 | harness generic; assertions go through the probe below |
| `scripts/lib/canvas-probe.mjs` | 66 | **100 % Minefield** — LIVES hearts, trail yellow, 32 px cells |
| `public/manifest.webmanifest`, `src/` changes | ~110 | content, and the score-profile line |

So roughly **700 lines transfer as-is, 300 do not.** But note what that number
does *not* capture: writing those 700 lines was the cheap part. The expensive
part was the five traps above (`ignoreVary`, `purpose`, the guard's placement,
the Safari container, the accept queue), and **those transfer through this
document whether or not the code is ever shared.**

### The seams

A shared tool would need exactly these values. Everything else is derivable:

| Config | Minefield's value | Used by |
|---|---|---|
| `name` / `shortName` | `The Strip` | manifest, `Info.plist`, zip + app + volume names, launcher text |
| `id` | `the-strip` | cache prefix, `.icns`/`.ico` names, `CFBundleExecutable`, archive names |
| `bundleId` | `io.github.zrebec.the-strip` | `CFBundleIdentifier` |
| `port` | `8137` | both servers, both launchers — **see the warning below** |
| `homepage` | `https://zrebec.github.io/minefield/` | the "play online instead" fallback in every failure path |
| `icon` | the SVG motif | every raster output |
| `themeColor` / `backgroundColor` | `#0000FF` / `#000000` | manifest, `<meta>` |
| `platforms` | web, macOS, Windows | which packagers run |

**The port is not a copyable constant — it must be allocated per game.** Two
zx-kit games both serving `127.0.0.1:8137` share an origin, and a service
worker's scope is origin plus path, so the second one does not sit beside the
first — it replaces it. Measured, two workers registered at `/` on one origin:

```
game A registered:        registrations: 1, controller: sw-a.js, caches: [game-a-v1]
game B, same port:        registrations: 1, controller: sw-b.js, caches: [game-a-v1]
```

The count stays at **1**: B took the scope rather than joining it, and from then
on B's precache answers for `/` — including for anyone who bookmarked game A.
Note the third column too: A's cache is still there, orphaned, because B's
`activate` only sweeps caches matching B's own prefix.

That prefix filter (`startsWith('the-strip-')`) exists because `github.io` is
one host for the whole portfolio, and there it is exactly right. It cannot help
here: it protects caches from each other, not scopes. The same shared origin
also merges `localStorage`, so the games' save keys would have to stay
namespaced by hand.

A shared tool must therefore **hand out ports and record them**, not default
them — and the ports have to be part of the shared config, not each game's
private constant, or the collision is only a matter of time.

### What should stay per-game

`canvas-probe.mjs` is the honest boundary. Every line of it knows something
about Minefield — the red LIVES hearts that prove a run is live, the bright
yellow of a walked trail on grass, `CELL × SCALE = 32`. No other game will share
those. So the split for the proofs is: a shared tool could own the **harness**
(seed a cache, cut the network, kill the server, cold-start a persistent
profile) and take a game-supplied `isRunning()` probe as a callback. The harness
is the part that took the debugging; the probe is the part only the game can
write.

Likewise the launcher *wording* should stay with the game. The structure is
mechanical, but "Waiting for your browser to take its copy…" is the game's
voice, and a tool that centralises copy ends up with a strings file nobody owns.

### Shape, if it is ever built

A **build-time CLI, not a runtime dependency** — `npx zx-pack` reading `dist/`
plus a small config. That matters because every project here is its own git
repository (`retro/` is not a repo), so anything shared has to be published or
vendored. A build tool that breaks breaks a build; a runtime dependency that
breaks breaks the game in a player's browser, and it would have to be
version-bumped through three games to fix.

**Open, and genuinely unknown today:** whether ChaosBunny or IceHaul want a
desktop app at all, or whether the itch.io web build plus browser install covers
them. Designing the packagers before one of them answers that is designing
against one real case and two imagined ones — which is the failure mode the
2nd-consumer rule exists to prevent.
